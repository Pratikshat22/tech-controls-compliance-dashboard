================================================================================
DAX MEASURES
Technology Controls & Compliance Monitoring - Power BI Data Model
================================================================================
NOTE: The data is simulated (generated with a Python script), not real company
data. This file shows the method, not real findings.

How to use: In Power BI Desktop, open Model view, right-click Fact_ControlTest
(or the table named in the section), then choose New Measure and paste.
Add the calculated columns in Section 0 first. Some measures depend on them.

Every measure has a short comment saying what it does and why it is written
that way.

NOTE ON DATES: Measures that use TODAY() change every day the report is
opened. The dataset itself was generated "as of" 19-Sep-2026.

================================================================================
SECTION 0 - CALCULATED COLUMNS (build these first)
================================================================================

-- Fact_ControlTest has three dates: test date, remediation open date and
-- remediation close date (plus a due date). Only TestDateKey has an active
-- relationship to Dim_Date, and it is used for trends.
-- The remediation dates are turned into normal Date columns with LOOKUPVALUE.
-- This avoids extra relationships and USERELATIONSHIP in every aging measure.
-- These columns are used only inside DATEDIFF and filters.

Fact_ControlTest[RemediationOpenDate] =
LOOKUPVALUE(Dim_Date[Date], Dim_Date[DateKey], Fact_ControlTest[RemediationOpenDateKey])

Fact_ControlTest[RemediationDueDate] =
LOOKUPVALUE(Dim_Date[Date], Dim_Date[DateKey], Fact_ControlTest[RemediationDueDateKey])

Fact_ControlTest[RemediationCloseDate] =
LOOKUPVALUE(Dim_Date[Date], Dim_Date[DateKey], Fact_ControlTest[RemediationCloseDateKey])

-- A "Pass" row has no remediation key, so the date is blank. That is what we
-- want: Pass rows should not enter any aging calculation.


================================================================================
SECTION 1 - BASE COUNTS
================================================================================

Total Control Tests = COUNTROWS(Fact_ControlTest)
-- Counts rows in whatever filters the visual already has (slicer, matrix row,
-- date range). Many ratio measures below divide by this.

Total Access Reviews = COUNTROWS(Fact_AccessReview)

Total Vendor Assessments = COUNTROWS(Fact_VendorAssessment)


================================================================================
SECTION 2 - CONTROL TESTING: EXCEPTION / FAILURE RATE
(Question: which control category or system is failing?)
================================================================================

Control Exceptions =
CALCULATE(
    COUNTROWS(Fact_ControlTest),
    Fact_ControlTest[TestResult] = "Exception"
)
-- CALCULATE adds one more filter (TestResult = "Exception") on top of the
-- existing filters. In a matrix cell for one System and one Category, all the
-- filters combine with AND.

Control Failures =
CALCULATE(
    COUNTROWS(Fact_ControlTest),
    Fact_ControlTest[TestResult] = "Fail"
)

Non-Effective Tests = [Control Exceptions] + [Control Failures]
-- Adds two smaller measures. Each one uses the current filters on its own.

Control Exception Rate % =
DIVIDE([Non-Effective Tests], [Total Control Tests])
-- DIVIDE is used instead of "/" because it returns blank (not an error) when
-- a cell has zero tests. Some System x Category cells can have no tests.

Control Failure Rate % = DIVIDE([Control Failures], [Total Control Tests])

% of Total Non-Effective Tests (Pareto share) =
DIVIDE(
    [Non-Effective Tests],
    CALCULATE([Non-Effective Tests], ALL(Dim_ControlCategory), ALL(Dim_System))
)
-- ALL() removes the Category and System filters only inside this CALCULATE.
-- So the bottom number is always the grand total of non-effective tests, and
-- each category shows its share of that total (used for a Pareto chart).


================================================================================
SECTION 3 - REMEDIATION AGING
(Question: how big is the open-exception backlog and how old is it?)
================================================================================

Open Remediation Items =
CALCULATE(
    COUNTROWS(Fact_ControlTest),
    Fact_ControlTest[RemediationStatus] IN {"Open", "In Progress"}
)

Avg Remediation Aging (Days Open) =
AVERAGEX(
    FILTER(
        Fact_ControlTest,
        Fact_ControlTest[RemediationStatus] IN {"Open", "In Progress"}
    ),
    DATEDIFF(Fact_ControlTest[RemediationOpenDate], TODAY(), DAY)
)
-- FILTER keeps only Open / In Progress rows. AVERAGEX then goes row by row
-- and finds the days from open date to today, and averages them.
-- This is a "right now" number and changes every day because of TODAY().
-- It is different from the next measure (time taken to fix closed items).

Avg Days to Remediate (Closed) =
AVERAGEX(
    FILTER(Fact_ControlTest, Fact_ControlTest[RemediationStatus] = "Closed"),
    DATEDIFF(Fact_ControlTest[RemediationOpenDate], Fact_ControlTest[RemediationCloseDate], DAY)
)
-- Only closed items. Shows how long a fix takes from open to close.

Aged Exceptions (60+ Days Open) =
CALCULATE(
    COUNTROWS(Fact_ControlTest),
    Fact_ControlTest[RemediationStatus] IN {"Open", "In Progress"},
    FILTER(
        Fact_ControlTest,
        DATEDIFF(Fact_ControlTest[RemediationOpenDate], TODAY(), DAY) > 60
    )
)
-- Two filters combined with AND: status is Open / In Progress, and days open
-- is more than 60. FILTER is needed because "days open" is a calculation, not
-- a plain column.

Aged Exception Rate % (of Open Backlog) =
DIVIDE([Aged Exceptions (60+ Days Open)], [Open Remediation Items])
-- The bottom number is open items only (not all tests). This answers: of the
-- items still waiting for a fix, how many are old?

Remediation Past Due Date (Severity-Based SLA Breach) =
CALCULATE(
    COUNTROWS(Fact_ControlTest),
    Fact_ControlTest[RemediationStatus] IN {"Open", "In Progress"},
    Fact_ControlTest[RemediationDueDate] < TODAY()
)
-- The due date was set when the exception was opened, based on severity
-- (Critical = 15 days, High = 30, Medium = 60, Low = 90). So this counts
-- items that missed their own deadline. It is kept next to the 60-day
-- measure because a Critical item can be late before it reaches 60 days.


================================================================================
SECTION 4 - ACCESS REVIEWS: ON-TIME %, ORPHANS, SEGREGATION OF DUTIES
================================================================================

% Access Reviews Completed On Time (30-Day SLA) =
VAR CompletedOnTime =
    CALCULATE(
        COUNTROWS(Fact_AccessReview),
        Fact_AccessReview[DaysOutstanding] <= 30
    )
RETURN
    DIVIDE(CompletedOnTime, [Total Access Reviews])
-- DaysOutstanding has a value for completed reviews (days taken) and for open
-- reviews (days elapsed so far). So an old open review counts as late right
-- away. If open reviews were left out, on-time % would look better than it is.

Orphaned Accounts (Distinct Users) =
CALCULATE(
    DISTINCTCOUNT(Fact_AccessReview[UserKey]),
    Fact_AccessReview[IsOrphanedAccount] = TRUE()
)
-- DISTINCTCOUNT is used instead of COUNTROWS because the same terminated user
-- can be flagged in more than one quarterly review. We want to count each
-- person once.
-- Orphaned account = account of a terminated employee that is still active.

Orphaned Account Rate % =
DIVIDE([Orphaned Accounts (Distinct Users)], DISTINCTCOUNT(Fact_AccessReview[UserKey]))

SoD Conflicts (Distinct Users) =
CALCULATE(
    DISTINCTCOUNT(Fact_AccessReview[UserKey]),
    Fact_AccessReview[HasSoDConflict] = TRUE()
)
-- SoD = Segregation of Duties. A conflict means one person holds two roles
-- that should not be combined (for example create and approve a payment).

SoD Conflict Rate % (of Reviewed Users) =
DIVIDE([SoD Conflicts (Distinct Users)], DISTINCTCOUNT(Fact_AccessReview[UserKey]))

Avg Days to Complete Review =
CALCULATE(
    AVERAGE(Fact_AccessReview[DaysOutstanding]),
    Fact_AccessReview[ReviewStatus] = "Completed"
)
-- Only completed reviews. This measures speed of finished reviews. The on-time
-- measure above includes unfinished reviews, so the two answer different
-- questions.


================================================================================
SECTION 5 - WHAT-IF PARAMETER: ACCESS REVIEW SLA (30 -> 15 DAYS)
================================================================================

BUILD STEPS (Power BI Desktop):
  1. Modeling ribbon -> New Parameter -> Numeric range.
  2. Name: "Access Review SLA (Days)"
  3. Data type: Whole number | Minimum: 10 | Maximum: 45 | Increment: 5 |
     Default: 30.
  4. Power BI creates a table with the same name (not connected to other
     tables) and this measure:
        Access Review SLA (Days) Value =
            SELECTEDVALUE('Access Review SLA (Days)'[Access Review SLA (Days)], 30)
  5. Add a Slicer using this new table's field. This is the slider users move.

WHY THE PARAMETER TABLE IS NOT CONNECTED:
  SELECTEDVALUE just reads the number chosen on the slicer (like 15). It does
  not filter any fact table. If the table were connected, moving the slider to
  15 would try to filter Fact_AccessReview rows by that value, which is not
  what we want. We want 15 to be used as a number inside a formula.

Measures built on the parameter:

On-Time % (Dynamic SLA) =
VAR SelectedSLA = [Access Review SLA (Days) Value]
VAR OnTimeCount =
    CALCULATE(COUNTROWS(Fact_AccessReview), Fact_AccessReview[DaysOutstanding] <= SelectedSLA)
RETURN
    DIVIDE(OnTimeCount, [Total Access Reviews])

Backlog Count (Dynamic SLA) =
VAR SelectedSLA = [Access Review SLA (Days) Value]
RETURN
    CALCULATE(COUNTROWS(Fact_AccessReview), Fact_AccessReview[DaysOutstanding] > SelectedSLA)

Incremental Backlog vs Current 30-Day SLA =
VAR SelectedSLA   = [Access Review SLA (Days) Value]
VAR BreachSelected = CALCULATE(COUNTROWS(Fact_AccessReview), Fact_AccessReview[DaysOutstanding] > SelectedSLA)
VAR BreachAt30     = CALCULATE(COUNTROWS(Fact_AccessReview), Fact_AccessReview[DaysOutstanding] > 30)
RETURN
    BreachSelected - BreachAt30
-- Idea: keep reviewers' past behavior the same (DaysOutstanding does not
-- change when the slider moves) and ask how many of the same reviews would
-- be late under a stricter SLA. A positive result means extra late reviews
-- if the SLA is tightened. A negative result (looser SLA) means fewer.
-- This is a simple first estimate. It does not include extra staff,
-- automation or process changes.
-- The exact numbers for this dataset are in the findings file.

SECTION 6 - THIRD-PARTY / VENDOR RISK
================================================================================

Vendors Overdue for Reassessment =
CALCULATE(
    DISTINCTCOUNT(Fact_VendorAssessment[VendorKey]),
    Fact_VendorAssessment[IsLatestAssessment] = TRUE(),
    Fact_VendorAssessment[OverdueForReassessment] = TRUE()
)
-- Only the latest assessment of each vendor is checked. An old assessment that
-- has already been replaced should not make a vendor look overdue.

% Vendors Overdue for Reassessment =
DIVIDE([Vendors Overdue for Reassessment], DISTINCTCOUNT(Dim_Vendor[VendorKey]))

High-Risk Vendors with Open Findings =
CALCULATE(
    DISTINCTCOUNT(Fact_VendorAssessment[VendorKey]),
    Fact_VendorAssessment[IsLatestAssessment] = TRUE(),
    Fact_VendorAssessment[InherentRiskTier] = "High",
    Fact_VendorAssessment[OpenFindingsCount] > 0
)

Avg Open Findings per Vendor (Latest Assessment) =
CALCULATE(
    AVERAGE(Fact_VendorAssessment[OpenFindingsCount]),
    Fact_VendorAssessment[IsLatestAssessment] = TRUE()
)

Total Critical Vendor Findings (Latest Assessment) =
CALCULATE(
    SUM(Fact_VendorAssessment[CriticalFindingsCount]),
    Fact_VendorAssessment[IsLatestAssessment] = TRUE()
)


================================================================================
SECTION 7 - RISK HEAT MAP (System x Control Category matrix)
================================================================================

Build steps:
  1. Insert a Matrix visual.
  2. Rows: Dim_ControlCategory[CategoryName]. Columns: Dim_System[SystemName].
  3. Values: [Control Exception Rate %].
  4. Format -> Cell elements -> add a rule -> Format style: Color scale.
     Field: [Control Exception Rate %]. Minimum color = green (#2E7D32),
     Midpoint = yellow (#F9A825) at about 15%, Maximum color = red (#C62828)
     at about 30% or more.
  5. Add [Total Control Tests] as a tooltip field. Some cells have very few
     tests, so a high rate on a small number of tests should not be read as
     strongly as the same rate on a large number.

No new measure is needed for the heat map. [Control Exception Rate %] already
works in every cell, because each cell gives it a different System and
Category filter.
